# Repeated Booking creates a Recurring Booking Series through its own Start booking form, not the Timetable

Repeated is now bookable. Choosing Repeated at Start booking's One-time vs Repeated step continues to a new "recurring occurrence form" step (`recurring_when`) instead of the Timetable's date-and-time `when` step. That form collects First occurrence, Last occurrence, one shared local start–end time window, and a room selection, then submits directly to `POST /api/v1/facility/booking-series` (core-api#148). A successful create shows a Pending-payment result — total, hold deadline, and the initial occurrence — inline on the same Start booking page; it does not navigate to `/rooms` or `/booking-details`.

The Timetable's own Search Bar Repetition control is intentionally left as `disabled`, one-time-only (ADR 0001's original reasoning). A weekly Recurring Booking Series has no per-day pin/ADD/Confirm Booking Time interaction to offer — the member is committing to a range of future dates at once, not one calendar day — so bolting it onto the single-day grid architecture (ADR 0022/0023/0026) would fight that architecture rather than reuse it. Supersedes ADR 0001: Repeated is no longer permanently blocked, but it still never reaches the Timetable in this slice.

Two supporting choices, both driven by what core-api#148 actually exposes:

- **Room picker reuses the one-time availability endpoint for catalog data only.** There is no standalone room-catalog endpoint and no conflict-preview endpoint yet (conflict review and Priority Ministry override are core-api's follow-up ticket, see ADR 0019 in newlife-core-api). The recurring form calls `facilityService.getAvailability(firstOccurrenceDate, ministryId)` once First occurrence is chosen and only reads room id/name/capacity/photo from the result — the per-day occupancy `cells` are irrelevant to a multi-week series and are discarded.
- **Client-side validation is structural only; business-rule validation is server-driven.** The client checks what is unambiguously computable from the request shape alone — date ordering, same-weekday First/Last occurrence, same Use Period, end-after-start time, at least one room selected. It does **not** attempt to precompute the availability window or the minimum-occurrence count, because those System Settings (`facility.recurring_booking_availability_window`, `facility.min_recurring_booking_weeks`) have no member-facing read endpoint. Submitting maps the backend's `error_code` (`FACILITY_RECURRING_*`, `FACILITY_BOOKING_*`) to a friendly i18n message via `resolveRecurringBookingSeriesErrorMessage` (mirroring the existing `resolveMinistryApplicationErrorMessage` pattern), so window/minimum/conflict/blackout/DST errors still surface before the member believes the booking succeeded — they just aren't pre-validated client-side.

## Consequences

- The success view holds its result only in React state, not the URL or localStorage — unlike Payment (which reloads by booking id) or Booking Details (which reloads by Draft id), there is no member-facing "get Series by id" endpoint yet to reload from. A refresh on the success view loses it; this is accepted as a this-slice gap, not solved here.
- Because the availability window and minimum-occurrence count are not readable client-side, the form cannot proactively disable an out-of-window or too-short range before submit — the member finds out from the server error after clicking Create booking series. This is expected to improve once/if a settings-read endpoint exists.
- Conflict review, exclusions, and Priority Ministry override (core-api#148's deferred scope) are also deferred here: a room/blackout conflict on any occurrence fails the whole create with a single error and no way to omit just that date. That flow is explicitly out of scope for this ticket (frontend issue #98).
